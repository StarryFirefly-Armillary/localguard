# LocalGuard QLoRA adapter — held-out evaluation decision

Date: 2026-11-20

## Outcome

The QLoRA adapter at `<training-dir>\adapter-r16` is **NOT merged and NOT deployed**.
The Stage 5 acceptance gate (`localguard.training.compare_evaluations`) FAILED.

## How this was measured

- Harness: `<repo>\scripts\evaluate_holdout.py`
- Both `before` (base model) and `after` (base + LoRA adapter) were generated by
  REAL 4-bit NF4 inference on the local RTX 5070 GPU, using the same fixed prompt
  and `enable_thinking=False`. No prediction, score, label or location was invented.
- Held-out set (7 samples): the 2 genuine `tool_call` held-out records as positives
  (ground truth CWE-1321 at `index.js:71` / `:73`), 2 clean fixtures and 3 held-out
  `safe_implementation` snippets as hard negatives.
- Raw model answers are preserved in `raw_answers.json`; the exact evaluation rows
  in `before.json` / `after.json`; the sample definitions in `samples.json`.

## Gate result

`python scripts/train_adapter.py evaluate --before <abs>/before.json --after <abs>/after.json`
exited 2 with:

- `passed: false`
- reason: `false_positive_rate: no measurable improvement`
- before: detection_accuracy 0.714, FPR 0.4, cwe_accuracy 0.0,
  exact_line_accuracy 0.5, tool_format_success 1.0, AUC 0.7
- after:  detection_accuracy 0.714, FPR 0.4, cwe_accuracy 0.0,
  exact_line_accuracy 0.5, tool_format_success 1.0, AUC 0.8

## Why no improvement is expected (structural, not a harness defect)

1. The curated `tool_call` records only contain POSITIVE examples.
   `localguard/training.py::_validate_tool` explicitly rejects an empty `issues`
   array ("Tool source requires structured validated issues"), so the training
   set cannot teach the model to emit "no issues" for clean code.
2. The local interaction database contains **zero** `location_rejected` rows.
   `ingest_logs()` can only surface such rows as `negative_examples`, and there are
   none to ingest. Both negative paths described in the task book are therefore empty.
3. The adapter was trained for 5 optimizer steps (`checkpoint-5/trainer_state.json`,
   `max_steps: 5`, `best_metric: null`) on a 20-record seed corpus. There is no
   measured improvement to claim even if negatives were available.

## Follow-up (same day, 18:50+): negatives built, retrain blocked by host

Internet research confirmed the diagnosis and the standard remedy: train on
balanced positive/negative data. Naive positive-only fine-tuning of code models
is documented to collect "flaws" while being unable to reject false positives.

Work completed in the follow-up:
- Added an optional, strictly validated fourth training source `clean_evidence`
  (`localguard/training.py`). A record is accepted only if a genuine `view_file`
  log AND a genuine logged zero-finding `patterns` scan with a hash-matching
  saved artifact corroborate it; `issues` must be `[]`. Six unit tests
  (`tests/test_clean_evidence.py`) confirm fabricated records are rejected.
- Built `scripts/collect_clean_evidence.py` and generated 23 genuine negative
  records (11 clean fixtures + 12 TRAIN-split safe implementations; zero heldout
  CVE overlap) at `.localguard/curation/clean_evidence.jsonl`.
- Built `scripts/evaluate_aligned.py` to test in the exact tool-call training
  format; that format produced no parseable output from either model in 5 steps,
  so the original `evaluate_holdout.py` remains the valid detection measurement.
- Added opt-in `--no-gradient-checkpointing` / `--max-length` to the training CLI;
  default behaviour and VRAM safety are unchanged.

Remaining blocker: retraining on this host is not tractable. Qwen3.5-4B is an
`AutoModelForImageTextToText`; optimized `causal-conv1d`/`flash-linear-attention`
kernels are unavailable as prebuilt wheels for this CUDA/Python build (source
build fails without the CUDA toolchain). With reference kernels, one
checkpointed step takes minutes (11 steps ≈ hours); without checkpointing the
run OOMs on 8GB. Multiple attempts were stopped rather than left running for hours.

Status unchanged: no adapter is merged or deployed. The deterministic core is the
delivery boundary. To finish Stage 5 on hardware with working kernels (or a
smaller text-only base), run:
  train_adapter.py train --data data/train.jsonl <curation>/clean_evidence.jsonl \
    --base-model <base> --output <new-adapter> --rank 16 --epochs 2
  evaluate_holdout.py (with LOCALGUARD_EVAL_ADAPTER set to the new adapter)
  train_adapter.py evaluate --before <...>/before.json --after <...>/after.json
Merge only if that gate passes; do not weaken the gate or fabricate predictions.
